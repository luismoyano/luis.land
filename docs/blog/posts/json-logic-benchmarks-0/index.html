You can't benchmark what you can't compare - The problem with benchmarking JSON Logic gems in Ruby

Part 0 of a series on making the fastest AND most compliant Ruby JSON Logic gem.

Before I talk about performance at all, I need to talk about a problem that makes benchmarking JSON Logic gems in Ruby genuinely tricky — and that most people ignore entirely; the gems don’t do the same thing.

A bit of context

JSON Logic is a spec loosely based on S-expressions where business logic and data are expressed in JSON and the output should be predictable across languages. The idea is that you write a rule once and it works identically in your JavaScript frontend, your Python backend, and your Ruby service.

The Ruby ecosystem has several gems:

  • json_logic — the oldest one, utterly abandoned and last updated 4 years ago
  • json-logic-rb — better maintained, more active, usually filled with very naive errors.
  • json_logic_ruby — lastly updated on 2024.
  • shiny_json_logic — mine

Now here’s the thing. The official JSON Logic test suite has 601 tests. Let me show you what happens when you run them against each gem:

Gem Tests passing
shiny_json_logic 601 / 601 (100%)
json-logic-rb ~403 / 601 (67%)
json_logic ~375 / 601 (63%)
json_logic_ruby ~254 / 601 (42%)

So when you benchmark these gems against each other, what exactly are you measuring?

If I run all 601 tests and json_logic processes 375 of them “fast” while skipping or erroring on the other 226. Is that faster? It shouldn’t be, It’s doing less work than a gem that actually passes everything. How can we even compare apples to apples?

The two modes

This is what led me to design the benchmark in two modes:

All tests. Running all 601 official tests through every gem and the ones that error get counted as zero time.

Fair comparison. By finding the intersection of tests that all gems pass, and benchmark only on those to resemble an even scenario where they’re all doing the same work.

The difference between these two modes is revealing because a gem that’s “faster” in Mode 1 might just be faster at failing, using a fair ground levels the ground to correctly understand how a gem benchs against other.

But then, why should we even benchmark with all tests? The reason is that given the case where we allow the competition between two gems where one provides way more features than the other, we should still be able to measure the performance of those features that would be unnoticed otherwise.

Why does this matter?

If you’re evaluating JSON Logic gems and you only look at ops/s, you might pick the wrong one because a gem at 63% compliance running at 80k ops/s is not faster than a gem at 100% compliance running at 70k ops/s, it just breaks faster.

The benchmark infrastructure I built is open source at github.com/luismoyano/jsonlogic_benchmarks. It runs both modes automatically across 9 Ruby versions on Linux CI.
